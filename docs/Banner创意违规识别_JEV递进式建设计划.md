## 1. 项目背景

当前创意违规识别依赖第三方审核能力。项目希望探索使用 JEV 决策模型识别
Bid Response
中的创意违规内容，评估现有模型能力是否能够覆盖部分审核场景，并为后续逐步降低第三方审核依赖提供依据。

在 OpenRTB（开放实时竞价协议）响应中，创意内容通常通过 `adm`（Ad
Markup，广告标记）返回。`adm` 可能是静态 HTML，也可能包含 JavaScript
Loader、外部图片、Iframe、MRAID 等动态内容。仅把原始 ADM
字符串交给决策模型，并不能保证模型实际看到了最终展示素材。因此，建设重点不仅是模型判断，还包括
ADM 解析、素材提取、证据关联、规则检测和结果评估。

## 2. 项目目标与非目标

### 2.1 建设目标

1.  输入一条 Bid Response，提取本条 Response
    中实际包含的创意素材和相关字段。
2.  以 Banner 图片创意为第一期对象，识别约定的 11 类违规标签。
3.  对每个标签输出命中状态与可追溯证据；仅在 Hub 确实提供且语义明确时保留分数，只有经过概率语义与校准验证的值才称为概率，不承诺模型必然返回自由文本解释。
4.  对同一份固定输入，在固定模型与规则版本下，尽可能保证结果可复现。
5.  将 JEV 结果与 TMT 离线审核结果进行对照，使用人工复核样本评估准确性。
6.  明确哪些样本可由模型给出较高把握的判断，哪些样本必须继续交由 TMT
    或人工复核。

### 2.2 第一阶段非目标

-   不覆盖 Video、Native 创意审核。
-   不以打开落地页、访问广告点击目标的方式补充当前 Response
    未提供的信息。
-   不直接执行不可信的第三方 JavaScript。
-   不在 POC 阶段改变线上审核决策或自动拦截策略。
-   不让 JEV 承担 HTML 渲染、任意脚本执行或不受控资源抓取；直接输入图片不等于只提交图片 URL 就能完成审核。
-   不在验证 JEV 图文直判效果之前，强制建设独立 OCR 或视觉特征模型流水线。
-   不以 JEV 与 TMT 的一致率作为唯一成功标准。

## 3. 总体建设原则

1.  **先取得素材，再图文判断**：由确定性程序解析 Response 和 ADM、获取图片和可见文案，再通过自有 Hub 将真实图文内容交给 JEV；结构化元数据用于关联与追溯，不替代原始图像。
2.  **证据优先**：每个标签结论都必须关联可追溯证据，不能只输出一个标签或分数。
3.  **未知不等于合规**：素材缺失、解析失败、动态资源无法取得时，应输出
    `UNKNOWN` 或检测不完整，不能默认判为未违规。
4.  **规则与模型分工**：可确定性判断的规则（如 URL 是否使用
    HTTP）优先由规则模块完成，不依赖视觉模型。
5.  **先离线、后影子、再评估**：先构建固定数据集，之后进行 TMT 对照和
    Shadow Mode（影子模式），通过门槛后再讨论线上切换。
6.  **版本可追溯**：必须记录输入素材、模型、提示词/决策配置及规则版本，保证结果可以复盘。
7.  **安全隔离**：任何需要加载动态 ADM
    的操作都必须运行在受控隔离环境，不能在网关主进程或开发人员日常浏览器中直接执行未知脚本。
8.  **先验证 Hub 和最小样本**：先核验文本、图片、标签输出及异常处理，再扩展解析和评估流程；OCR 或独立视觉模型只有在对照实验显示必要时才引入。

### 4.1 标签边界重点

-   **Nudity 与 Sexually
    Suggestive**：前者关注实际裸体或规定身体部位裸露；后者关注未裸体但明显的性暗示。
-   **Dating 与 Adult
    Entertainment**：前者是约会、婚恋、匹配服务；后者是成人内容、直播、色情陪聊等。
-   **Gambling**：重点识别下注、真实货币或有价值筹码、赢钱承诺等语义；普通游戏机制不能直接视为赌博。
-   **Religion
    Spirituality**：不能仅凭宗教建筑、图案或文化符号判定，应结合传播、信仰、灵修、占卜或募捐语义。
-   **Unsecured Request**：检查实际使用的资源 URL，而不是对整个 ADM
    做简单字符串包含判断。需要在规则中明确是否纳入 `nurl`、`burl`
    等通知地址；建议将"创意资源 URL"和"竞价通知
    URL"分开统计，待业务策略确认后决定是否纳入标签。
-   **未知素材**：如果动态资源未能成功提取，相关视觉标签应是
    `UNKNOWN`，而不是 `NOT_HIT`。

### 4.2 标签与检测能力映射

系统仍输出 11 类标签：10 类视觉/语义标签优先通过 Hub 交给 JEV 直接判断，Unsecured Request 由确定性规则生成。各类效果是否达标通过 POC 验证，不因模型支持图片就预设识别质量。

| 标签 | 主要输入 | 推荐责任模块 |
| --- | --- | --- |
| Dating | 图片/截图、可见文案 | JEV 图文判断 |
| Gambling | 图片/截图、可见文案 | JEV 图文判断 |
| Nudity | 图片/截图 | JEV 图像判断 |
| Sexually Suggestive | 图片/截图、可见文案 | JEV 图文判断 |
| Marijuana (THC) | 图片/截图、可见文案 | JEV 图文判断 |
| Adult Products | 图片/截图、可见文案 | JEV 图文判断 |
| Adult Entertainment | 图片/截图、可见文案 | JEV 图文判断 |
| Profane Language | 图中文字、ADM 可见文案 | JEV 图文判断；OCR 可选辅助 |

## 5. 总体技术架构

### 5.1 模块划分

以下为逻辑职责，POC 可以在同一后端内实现，不要求拆成独立服务。

| 模块 | 主要职责 | 责任边界 |
| --- | --- | --- |
| Response 接入层 | 保存 Bid Response，提取 `adm`、`adomain`、`crid`、尺寸和请求关联信息 | 项目后端 |
| ADM Parser | 解析 HTML、可见文案、图片、脚本、Iframe、资源引用和点击地址 | 不负责视觉理解 |
| Asset Extractor | 安全获取真实图片；动态阶段获取隔离渲染截图；记录内容 hash 与失败原因 | 不执行合规判断 |
| 多模态输入组装 | 组合图像内容、可见文案、来源 ID、标签定义和完整性状态 | 不先把图像压缩为推测性描述 |
| OCR / 外部视觉增强（可选） | 在实测发现短板后补充识别或定位信息 | 非基础链路前置条件 |
| Hub Client | 后端鉴权、`/v1/responses` 请求适配、超时控制与原始响应留存 | 客户端不直连 TypeSafe 原生 API |
| JEV 多模态判断 | 经 Hub 调用 `jev-1.14`，直接理解图片和文本，判断 10 类视觉/语义标签 | 能力与输出形式需联调验证 |
| Rule Engine | 检测 Unsecured Request 等确定性规则 | 不依赖模型分数 |
| Result Normalizer | 校验模型输出、证据关联与输入完整性，合并规则结果，生成 11 类统一结果 | 不编造缺失的分数、理由或证据 |
| Evaluation Pipeline | 与 TMT 及人工标注对照，计算分标签指标 | 离线评估 |
| Storage & Trace | 保存素材快照、调用关联、版本、原始结果与评估记录 | 密钥不入库、不入日志 |

### 5.2 逻辑数据流

``` text
Bid Response（如可用，关联原始请求上下文）
    |
    v
Response / ADM Parser
    |---- adm / crid / 可见文案 / 资源 URL / 动态依赖
    |
    +--------------------------------------+
    |                                      |
    v                                      v
Asset Extractor                        Rule Engine
    |---- 图片 / 可选截图 / hash            |---- Unsecured Request
    |---- 资源加载与完整性状态               |
    v                                      |
多模态输入组装（OCR 可选，不替代原图）        |
    |                                      |
    v                                      |
Hub Client: POST /v1/responses              |
    |---- model: jev-1.14                   |
    v                                      |
JEV 图文判断（10 类视觉/语义标签）           |
    |                                      |
    +------------------+-------------------+
                       v
              Result Normalizer
         （11 类结果 + 证据 + UNKNOWN）
                       |
                       v
              Result & Evidence Store
                       |
                       v
              TMT / 人工标注离线评估
```

### 5.3 模块边界要求

- ADM Parser 只负责结构解析与候选资源提取，不把脚本、注释或所有隐藏文本都当作实际展示内容。
- Asset Extractor 负责取得图片或说明失败原因；JEV 的图像能力不替代下载、渲染、安全隔离和加载完整性检查。
- 多模态输入组装保留原始图片/截图及其来源；hash 和内部资源 ID 仅用于追溯，不能替代实际发送给模型的图片内容。
- OCR / 外部视觉增强可补充事实信息，但必须保留来源与不确定性，不把推测写成事实。
- Hub Client 只使用后端密钥调用固定服务地址，依据联调后的协议适配；素材内容不能控制模型服务地址或鉴权信息。
- JEV 负责图像理解、文本语义与标签判断，不承担不受控网页抓取或任意脚本执行；完整标签定义和排除条件由项目侧维护。
- Rule Engine 独立检测 Unsecured Request；即使模型不可用，已取得证据的规则结果也可保留。
- Result Normalizer 按标签检查必要输入与输出字段；未返回的标签、无效结果或缺失的必要素材不得默认转换成 `NOT_HIT`。

## 6. Bid Response 与 ADM 解析建设

### 6.1 Response 字段提取

第一期至少保留以下字段（实际字段路径以项目当前接入的 OpenRTB
版本和数据结构为准）：

  字段                   用途
  ---------------------- ------------------------------------------------
  `crid`                 创意业务标识，便于关联和检索
  `adm`                  创意原始内容
  `adomain`              广告主域名，作为上下文信息，不单独作为违规证据
  `w` / `h`              Banner 尺寸
  `cat`                  广告类别上下文
  `attr`                 创意属性上下文
  `imp.secure`           原始 Bid Request 的关联上下文，不是 Bid Response 字段；缺失不能直接判违规
  `nurl` / `burl`        竞价通知地址，是否纳入 URL 标签范围需业务确认
  DSP / ADX / 请求标识   排查来源和链路问题

如只能取得 Bid Response，不补造 `imp.secure`；有原始请求时按 `bid.impid` 关联对应的 `imp`。一个 Response 中的多个 bid 分别建立素材与结果关联，不仅依赖 CRID 聚合。

### 6.2 ADM 类型识别

第一期需要识别但不限于以下形态：

1.  静态图片型：HTML 中直接引用图片资源。
2.  HTML5 动态广告型：HTML、CSS、JavaScript 组合。
3.  JavaScript Loader 型：由脚本继续加载素材或广告内容。
4.  Iframe 嵌入型：通过 Iframe 引用外部页面或广告内容。
5.  第三方 Ad Tag：由第三方标签继续控制素材加载。
6.  仅 Tracking Pixel 或追踪代码：可能没有可供视觉审核的主体素材。

这些类型可以同时存在，不应强制互斥。例如一个 ADM 可能同时包含
HTML、MRAID、JS Loader、图片资源和 Tracking Pixel。

建议为每条 ADM 记录以下解析元数据：

``` json
{
  "admType": ["HTML", "JS_LOADER"],
  "admLength": 12345,
  "hasImage": true,
  "hasVideo": false,
  "hasJavaScript": true,
  "hasIframe": false,
  "hasMraid": true,
  "parseStatus": "PARTIAL",
  "assetCount": 2
}
```

以上仅为建议结构示例，字段类型和枚举值应由工程实现统一定义。

### 6.3 素材提取策略

按复杂度逐级推进：

  --------------------------------------------------------------------------------------------------
  级别                    输入形态                第一阶段处理策略
  ----------------------- ----------------------- --------------------------------------------------
  L1                      直接图片 URL 或 `<img>` 解析 URL，按安全策略获取图片

  L2                      简单 HTML/CSS           提取图片、文字和必要样式信息

  L3                      HTML5 动态内容          在受控环境尝试渲染，提取截图及加载资源

  L4                      JS Loader / 第三方 Ad   先静态解析；必要时进入隔离渲染流程
                          Tag                     

  L5                      依赖 MRAID 或广告 SDK   标记环境依赖，单独验证，不作为第一批强制覆盖对象
                          环境                    
  --------------------------------------------------------------------------------------------------

### 6.4 动态 ADM 的处理原则

动态 ADM 的最终展示内容可能由外部 JavaScript
在运行时加载。不能假设静态解析 ADM 就能获得全部素材。

建议： - 先做静态解析，提取代码中明确声明的资源。 - 对允许处理的动态
ADM，在隔离浏览器或容器中尝试渲染。 -
记录渲染环境、加载成功/失败的资源、渲染耗时和最终截图。 - 对依赖 MRAID
或 SDK 的素材，明确标记环境不完整，不应将空白截图视为合规。 -
对远程资源设置域名白名单或受控出口策略、超时、大小限制和资源数量限制。 -
禁止点击广告、触发真实转化或主动访问落地页。 - 不允许在 ADX Gateway
主服务中执行第三方 ADM JavaScript。

## 7. 多模态输入、结果协议与 Hub 接入

### 7.1 JEV 的输入定位

优先输入真实图片/截图与可见文案，让 JEV 直接进行视觉和语义判断；结构化信息负责描述素材来源与检测边界，不要求先用另一个模型生成图片特征。

项目内部的多模态输入包包括：

- 与当前 bid 关联的基础字段与 ADM 解析结果；仅发送审核必要信息。
- 真实图片/截图内容，以及稳定 `sourceId`、内容 hash、来源地址和采集时间；内部 ID 和 hash 不能作为图片本身的替代输入。
- 解析得到的可见文案及其原始位置。
- 可选 OCR 文本及其来源；未启用 OCR 或 OCR 失败本身不意味着视觉审核一定失败，应按实际图像可读性和该标签所需证据判断。
- 资源加载与动态依赖状态、当前输入完整性；URL 清单交给规则模块，不要求 JEV 重复判断协议。
- 10 类视觉/语义标签的定义、排除条件和已验证的结果要求。

优先由后端安全获取并固定图片内容，再按 Hub 已验证的格式发送；若采用 Hub 拉取图片 URL 的方式，需要另行验证安全策略以及实际送审内容与快照一致性。仅把 URL 写进普通文本不算图片输入。

图片、ADM 文案和 OCR 内容均是不可信的待审数据，其中出现的“忽略规则”等指令不能覆盖审核规则；输入组织与回归测试需要覆盖此类提示词注入样本。

模型调用统一经过自有 Hub，已确认的接入信息见 7.6；完整请求体、图片承载方式和返回字段以 Hub 联调结果为准，不把 TypeSafe 原生 API 协议直接套用到 Hub。

### 7.2 每类标签的输出

以下是项目统一结果协议，不是要求 Hub 原样返回这些字段；由 Result Normalizer 合并模型判断、规则检测与系统状态后生成：

- `score`：可选数值；仅在原始响应存在且确认语义时填入，否则为 `null`，并在运行记录中保存原始字段、分数定义和映射版本。
- `probability`：可选命中概率，仅在概率语义和校准通过验证后提供，否则为 `null`；不能把任意 `score` 或对所选类别的 `confidence` 直接当作命中概率。
- `status`：`HIT`、`NOT_HIT` 或 `UNKNOWN`，依据有效判断、输入完整性和标签规则确定，而非只靠通用数值阈值。
- `evidence`：关联到真实送审字段、图片、截图或文本片段；不接受不存在的来源 ID。
- `reason`：模型确实返回的说明，或系统可验证的规则/失败原因；不支持时允许为 `null`，不能补写未观察到的画面细节。
- `reviewRequired`：是否需要复核；POC 结果均进入离线对照，不据此自动放行或拦截。

建议示例（假设接口已能返回对应判断与证据，数值仅为格式演示，尚未校准为概率）：

``` json
{
  "crid": "example-crid",
  "labels": {
    "Dating": {
      "score": 0.08,
      "probability": null,
      "status": "NOT_HIT",
      "evidence": [
        {
          "sourceType": "IMAGE",
          "sourceId": "asset-001"
        }
      ],
      "reason": "未发现约会或婚恋匹配服务推广证据",
      "reviewRequired": true
    },
    "Gambling": {
      "score": 0.91,
      "probability": null,
      "status": "HIT",
      "evidence": [
        {
          "sourceType": "IMAGE",
          "sourceId": "asset-001",
          "description": "图片中出现下注及赢钱相关信息"
        }
      ],
      "reason": "素材包含下注和赢钱号召",
      "reviewRequired": true
    },
    "Nudity": {
      "score": null,
      "probability": null,
      "status": "UNKNOWN",
      "evidence": [],
      "reason": "Hub 未返回该标签的有效判断",
      "reviewRequired": true
    }
  }
}
```

该 JSON 不是 Hub 请求体或原始返回样例，不能据此推定自由文本解释、区域定位或分数能力已经可用。上例的视觉正例仅在已获取图像中有可追溯证据时成立；如存在未取得的动态素材，依赖这些素材的标签仍为 `UNKNOWN`。

### 7.3 状态定义

  -------------------------------------------------------------------------------------------------------------
  状态                    含义                                 适用条件
  ----------------------- ------------------------------------ ------------------------------------------------
  `HIT`                   有足够证据支持命中                   证据明确，且满足标签定义

  `NOT_HIT`               已完成必要检测，未发现该类违规证据   输入完整度满足该标签的检测要求

  `UNKNOWN`               当前证据不足，无法可靠判断           素材缺失、解析失败、资源不可用、模型无法判断等
  -------------------------------------------------------------------------------------------------------------

**重要：`NOT_HIT`
不等于"绝对合规"，只表示在当前定义和检测范围内没有命中该标签。**

### 7.4 证据规范

证据应尽可能定位到原始来源，建议支持：

-   `sourceType`：`ADM_FIELD`、`IMAGE`、`SCREENSHOT`、`OCR_TEXT`、`RESOURCE_URL`
    等。
-   `sourceId`：本次检测中稳定的素材标识。
-   `fieldPath`：例如 `seatbid[0].bid[0].adm`。
-   `assetHash`：素材内容 hash。
-   `text` / `description`：必要的文本或描述。
-   `location`：图片区域或截图区域；如当前检测能力不支持，可暂不提供。
-   `detector`：证据来源模块及版本。

不能只输出"疑似违规"而没有可追溯依据。模型输入的来源清单不自动等于某个标签的命中证据：若多图请求只返回总体标签而无素材对应关系，应补做逐素材核验或人工复核；若必须结合整体版式判断，则以对应截图作为送审来源，不能随意指派某一张图。

`reason` 与区域坐标只在确实获得时保存；素材关联可由系统通过调用记录建立，画面描述和区域定位不能由系统凭空补齐。缺乏可追溯命中证据的输出保留为待复核候选，统一状态为 `UNKNOWN`、`reviewRequired: true`，不生成最终 `HIT`。

### 7.5 分数与阈值策略

探索总结中的初始规则：

-   概率 `>= 0.85`：作为高置信候选命中，进入 TMT 离线验证。
-   概率 `<= 0.30`：作为低命中概率的候选未命中，进入 TMT 离线验证。
-   `0.30 < probability < 0.85`：继续送 TMT。

这组阈值仅保留为原探索假设，只有 Hub 返回语义明确、量纲适用的命中分数或概率时才开展分层实验，不能直接套用到任意 `score`、`confidence` 或离散选项，更不能视为线上自动拦截阈值。

- 若 Hub 不提供可用数值，先评估分类结果与未知比例，不阻塞最小图文 POC，也不伪造概率。
- 不同标签的分数分布可能不同，不能默认共用同一阈值；未校准的分数统一称为 `score`。
- 低命中分数不等于“低判断置信度”，更不自动表示安全：缺图、无效响应和证据不足优先按完整性规则处理。
- 阈值在独立验证集上选择，最终根据每类 Precision、Recall、漏放风险和人工复核成本确定。

### 7.6 自有 Hub 接入协议与联调边界

#### 7.6.1 已确认的接入信息

以下信息来自项目方提供的调用约定，不代表已完成实际请求验证：

| 项目 | 约定 |
| --- | --- |
| HTTP 方法 | `POST` |
| 完整请求地址 | `http://49.0.206.228:80/v1/responses` |
| `baseUrl` | `http://49.0.206.228:80`（本方案约定不含 `/v1`） |
| 请求路径 | `/v1/responses`（与 `baseUrl` 拼接一次） |
| 鉴权请求头 | `Authorization: Bearer $AIHUB_API_KEY`，变量值由后端运行环境注入 |
| 内容类型 | `Content-Type: application/json` |
| 请求体模型字段 | `model`，取值 `jev-1.14` |

建议后端配置约定如下；除 `AIHUB_API_KEY` 外，其余环境变量名称属于本项目建议，不是 Hub 强制规范：

``` text
AIHUB_BASE_URL=http://49.0.206.228:80
AIHUB_MODEL=jev-1.14
```

`AIHUB_API_KEY` 通过后端环境变量或密钥管理服务注入，不写入文档、代码仓库、浏览器配置或日志。前端仅访问本项目后端，由后端携带密钥调用 Hub。

本项目不直连 TypeSafe 原生 `/v1/systemone` 接口，也不把 `/v1/responses` 的路径名称视为完整兼容任意 Responses 客户端的保证；除上表外，不预设完整请求体或响应 Schema。

#### 7.6.2 必须通过联调确认的能力

1. 文本输入字段、消息结构、角色及非流式返回方式；先取得脱敏的最小成功请求/响应样本，再固化适配协议。
2. 图片在 JSON 请求中的表示方式，例如 data URL/base64、资源标识或图片 URL，以及多图、格式、尺寸和请求大小限制；这些都是待核验选项，不代表 Hub 已支持。
3. 图片必须实际到达 JEV：用相同指令、不同图片及去掉图片的对照测试区分视觉输入生效和仅依据文字作答，不能仅凭 HTTP 200 判断成功。
4. 标签、结构化输出、分数和证据的返回形式；核实是否存在 `noul`、`choice`、`score`、`box` 等原生能力的 Hub 映射，不假定这些就是 `/v1/responses` 的可用请求字段。
5. 上游图像能力所需的实验性选项是否由 Hub 内部处理、是否需要透传；在未确认前，不把 `TypeSafe-Danger-Zone-Images` 等原生请求头设为本项目必填项。
6. 区分命中分数、命中概率、分类置信度与其他数值；没有语义明确的分数字段时保持空值，不从解释文字臆造概率。
7. 核验鉴权失败、模型不存在、图片被拒绝、响应不完整、限流和超时的错误格式，并明确超时/重试预算，避免不受控重复调用和计费。
8. 确认 `jev-1.14` 对应的实际上游模型版本及映射变更机制；请求标识相同不等于模型版本永远不变。

TypeSafe 官方[模型说明](https://docs.typesafe.ai/models)与[图片输入说明](https://docs.typesafe.ai/go/images)用于理解上游能力，不作为自有 Hub 已支持对应字段、限制或请求头的证明。

#### 7.6.3 传输安全约束

当前提供的地址为 HTTP，Bearer 密钥及素材可能以明文传输；“自有 Hub”不等于链路已经加密。联调前需确认受保护的加密网络通道，或由 Hub 提供 HTTPS 入口，不直接通过未加密公网传输密钥和真实业务素材；本方案保留原地址，不推测可用的 HTTPS 地址。

Hub 鉴权仅发送给配置的模型服务，不随素材抓取请求或跨源重定向转发。Hub 地址本身不属于广告创意资源，不纳入 `Unsecured Request` 标签；其传输风险单独治理。

## 8. Unsecured Request 规则检测

Unsecured Request 与其他视觉/语义标签不同，应由 URL 规则模块独立检测。

### 8.1 检测对象

从 ADM 解析结果中提取真正被引用或使用的 URL，包括： - 图片资源 URL。 -
JavaScript/CSS 等资源 URL。 - Iframe URL。 - 其他实际加载的创意资源
URL。 - 点击跳转 URL（如果能从 ADM 中可靠解析）。

`nurl`、`burl`
等通知地址是否纳入该标签，需要业务方确认。建议单独采集和统计，避免与创意展示资源混为一谈。

### 8.2 判定原则

1.  对解析出的实际 URL 做 URI 解析，检查 scheme。
2.  `http://` 可作为命中候选。
3.  `https://` 不命中该规则。
4.  相对路径、无法解析的地址、动态拼接地址应记录为待确认或
    `UNKNOWN`，不能简单判合规。
5.  不能只对整个 ADM 做 `contains("http://")`
    判断，因为字符串可能出现在注释、示例文本或无实际执行作用的内容中。
6.  `imp.secure` 缺失本身不构成命中依据。

### 8.3 规则输出示例

``` json
{
  "Unsecured Request": {
    "status": "HIT",
    "score": null,
    "probability": null,
    "evidence": [
      {
        "sourceType": "RESOURCE_URL",
        "sourceId": "resource-001",
        "url": "http://cdn.example.com/banner.jpg",
        "scheme": "http"
      }
    ],
    "reason": "创意实际引用的图片资源使用 HTTP 协议"
  }
}
```

该类结果由规则引擎生成，不需要 JEV 给出视觉判断概率。

## 9. 数据集与人工标注建设

### 9.1 数据集组成

Phase 0 即准备少量已知标签、内容固定的图片与文本，验证 Hub 图文通路；随后逐步扩展为固定版本的离线数据集，不等全部工程模块完成后才收集样本。用于连通性和提示调试的样本归入开发集，不进入最终独立测试集。

数据集至少包括：

1.  正例：每个标签有明确违规证据的样本。
2.  反例：外观相似但不满足违规定义的样本。
3.  边界样本：容易混淆的标签边界。
4.  解析失败样本：ADM 不完整、资源失效、动态加载失败。
5.  复杂样本：多标签同时命中、一个 ADM 含多张图片或多个资源。
6.  真实线上抽样样本：用于观察自然分布，避免数据集只包含刻意构造的极端样本。

### 9.2 标注记录

建议每条样本保存：

  字段              说明
  ----------------- ----------------------
  `sampleId`        数据集内唯一 ID
  `crid`            业务创意 ID
  `admHash`         原始 ADM 内容 hash
  `assetHashList`   提取素材的 hash 列表
  `labelVersion`    标签规范版本
  `labels`          11 类人工标注结果
  `evidence`        人工标注依据
  `annotator`       标注人员标识
  `reviewStatus`    是否经过复核
  `createdAt`       标注时间

### 9.3 标注流程

1.  按统一的 11 类定义标注每个标签。
2.  每个命中标签必须附上证据。
3.  对边界样本增加说明，尤其是 Dating/Adult
    Entertainment、Nudity/Sexually
    Suggestive、Gambling/普通游戏、Religion/文化元素。
4.  对无法判断的样本标记为未知，不强行标注为反例。
5.  对争议样本由第二位标注者复核，必要时由业务审核负责人裁定。
6.  固化数据集版本，避免实验过程中无记录地修改标签。

### 9.4 数据集划分

建议至少区分： - 开发集：用于调试解析、特征和决策提示。 -
验证集：用于选择阈值和检查效果。 -
测试集：用于最终评估，避免反复调参污染。

同一个素材的重复版本或近重复素材应尽量放在同一数据划分中，避免数据泄漏导致评估结果虚高。

## 10. TMT 对照实验与评估

### 10.1 实验流程

``` text
固定 Bid Response 样本
       |
       +------------------+
       |                  |
       v                  v
   JEV 流程             TMT 流程
       |                  |
       v                  v
  11 类结果             TMT 标签结果
       |                  |
       +---------+--------+
                 v
          人工复核/仲裁
                 |
                 v
          Ground Truth
                 |
                 v
       分标签指标与错误分析
```

### 10.2 第一轮验证标准

探索总结给出的初步成功标准： - 同一条 Response CRID
能重复运行并得到同一组标签。 -
每个标签能指出依据来自哪个字段或哪张图。 - 概率 `>= 0.85` 或 `<= 0.30`
的样本送 TMT 离线验证，准确率达到 90%。 - `0.30–0.85` 的样本继续送 TMT。

上述为原探索标准，并非 Hub 已具备的输出能力承诺。按 7.5 先验证数值是否适用；不支持可靠分数时，仍对分类结果进行 TMT/人工对照，但暂不报告基于这组阈值的高置信指标。

正式评估前明确“准确率 90%”的分母、未知样本处理方式及适用范围；同时按标签分别统计，报告 Coverage 和漏判风险，避免大量负例或排除未知样本后掩盖实际质量。同一 CRID 的稳定性验证需固定素材快照、Hub 映射及实际模型版本，而不只是业务 ID。

### 10.3 评估指标

  指标                    关注点
  ----------------------- ----------------------------------------------
  Accuracy                总体判断正确比例
  Precision               判为违规的样本中，实际违规比例
  Recall                  实际违规样本中，被识别出来的比例
  F1                      Precision 与 Recall 的综合指标
  False Negative Rate     违规素材被判为未命中的比例，重点关注漏放风险
  UNKNOWN Rate            无法判断的样本比例
  Coverage                系统能够给出非 UNKNOWN 结论的样本比例
  TMT Agreement           与 TMT 结果的一致程度，仅作为对照指标
  Latency                 单条样本处理耗时
  Parse Success Rate      ADM 解析成功率
  Asset Extraction Rate   素材提取成功率

### 10.4 结果分析要求

-   所有指标至少按 11 个标签分别统计。
-   分析误报和漏报的具体证据，而不仅仅记录最终分数。
-   对动态 ADM 单独统计解析失败、资源加载失败和渲染失败。
-   TMT 与 JEV 不一致时，使用人工复核结果判断哪一方正确。
-   对模型无法判断的样本，统计 `UNKNOWN` 原因分布。
-   不把 TMT 输出直接当作绝对 Ground
    Truth；必要时通过人工复核建立最终标签。

## 11. 可复现性与版本管理

### 11.1 为什么 CRID 不够

`crid` 是业务创意标识，但不能保证同一 CRID 对应的 ADM 内容永远不变。动态
Loader 还可能在不同时间加载不同远程素材。因此只保存 CRID
无法保证实验可复现。

### 11.2 建议记录的版本维度

  `modelVersion`                      实际上游 JEV 版本；Hub 未提供时明确标记未知

  `hubMappingVersion`                 Hub 路由/模型映射版本（若可获得）

  `hubAdapterVersion`                 项目侧请求、响应及分数映射协议版本

  `requestId`                         本地运行 ID 及 Hub 返回的请求 ID（若有），不含鉴权值

  `promptVersion` /                   决策配置或提示词版本（如适用）
  `decisionConfigVersion`             

  `ruleVersion`                       规则引擎版本

  `parserVersion`                     ADM Parser 版本

  `extractorVersion`                  素材提取版本

  `labelVersion`                      11 类标签定义版本

  -----------------------------------------------------------------------

### 11.3 幂等与重复运行

对相同的图文输入 hash、实际模型版本、Hub 适配版本、决策配置版本和规则版本，保存运行记录并支持重复执行。若底层模型本身存在非确定性，应记录随机性配置（如可用）、调用时间和原始响应，并通过重复运行实验测量稳定性，不应承诺未经验证的绝对确定性。

当前请求固定为 `jev-1.14`，不改用 `jev-latest`；同时需确认 Hub 的同名模型映射是否可能变化。若无法获知实际版本，应明确实验的可复现性限制，不能把模型标识相同当作版本冻结的证明。

## 12. 分阶段递进建设计划

### Phase 0：Hub 联调、最小样本验证与标签规范

**目标**：先证明 `jev-1.14` 经自有 Hub 能接收实际图文并给出可用判断，同时统一审核口径；不以完成整个素材流水线为前提。

工作项：

- 确认第一期只做 Banner，确定 11 类标签定义、正反例、边界与三态含义，以及 Unsecured Request 的 URL 范围。
- 在确认传输安全后，用后端 `AIHUB_API_KEY` 调用 `POST /v1/responses`，固定模型标识 `jev-1.14`；不把密钥放入前端。
- 准备少量本地固定图片和可见文案，完成纯文本、单图、图文组合、图片替换/移除对照；测试多图、坏图和失败响应的处理。
- 按 7.6 核验完整请求体、标签输出、可选分数/证据与实际模型映射，保存脱敏的成功及失败样例。
- 不以单次成功调用证明准确性，不以支持图片证明支持解释、区域定位或全部原生 primitive。
- 将联调用样本归入开发集，确定后续数据集字段、人工标注规范和评估口径。

**交付物**：Hub 最小调用验证结果、已核验的请求/响应协议、输入输出能力清单、最小开发样本集、标签规范草案。

**退出条件**：图像确实参与判断，标签结果可解析，缺失/失败不被转换成 `NOT_HIT`；明确分数和证据支持范围，首轮标签规范经业务审核确认。若 Hub 暂不支持图片，应先解决该阻塞或重新评审 OCR/外部视觉方案，不把纯文本调用冒充图文 POC。

### Phase 1：Bid Response / ADM 解析能力

**目标**：稳定提取素材候选及其来源信息。

工作项：

- 保存 Bid Response，逐 bid 提取 `adm`、`crid`、`adomain`、尺寸等；有原始请求时关联 `imp.secure`，无请求时不补造。
- 识别 ADM 类型，先支持静态图片、简单 HTML 和直接资源引用。
- 提取可见文案及图片、脚本、Iframe 和 URL，区分候选资源、动态依赖与已实际取得的素材。
- 生成来源 ID，记录位置与解析失败原因；素材内容 hash 在真正取得资源后生成。

**交付物**：Response Parser、ADM Parser、素材来源 Schema、解析测试样本和报告。

**退出条件**：静态与简单 HTML 样本可稳定解析，每个候选资源可追溯，解析失败不被误记为“无违规”。

### Phase 2：素材获取、多模态输入与规则检测

**目标**：为已经验证的 Hub 接口准备真实图像、文案和来源关系，同时完成确定性 URL 检测。

工作项：

- 实现图片安全获取、格式校验、大小限制和内容快照，生成 hash 与加载状态。
- 按 Phase 0 核验的协议组织图片和文案，保持每个来源 ID 与真正送入模型的内容一一关联。
- 实现 Unsecured Request，分别记录创意资源与通知地址；不把 Hub 服务地址纳入广告标签。
- 明确缺图、图片不可读和动态依赖时的完整性状态；本阶段不要求覆盖全部 JS Loader 或 MRAID。
- OCR 不作为退出门槛；只有后续图文基线显示必要时，再开展辅助提取对照。

**交付物**：Asset Extractor、多模态输入组装、URL Rule Engine、素材获取覆盖率报告。

**退出条件**：实际图文经 Hub 可送审、来源可追溯；URL 规则具备正反例；缺失素材不会被默认判为未命中。

### Phase 3：图文直判与 11 类结果闭环 POC

**目标**：形成 JEV 10 类视觉/语义判断与 1 类规则检测的统一结果，评估直接图文输入的效果。

工作项：

- 使用冻结的标签定义，通过 Hub 对真实图片/截图与文案进行判断，不强制先生成结构化视觉特征。
- 合并 Unsecured Request，生成 11 类统一结构；验证逐标签完整性与未知状态。
- 基于真实返回保存分数、解释与证据；不支持的可选字段留空，命中来源无法确认时转复核。
- 对固定样本重复运行，分析边界、多标签、多素材和输出缺项的情况。
- 如发现小字、语言或定位短板，对比图文基线与增加 OCR 的效果、延迟及成本；仅在收益明确时引入增强模块。

**交付物**：Hub 调用适配、统一结果 Schema、首轮离线预测、重复运行报告、必要时的 OCR 增益对照。

**退出条件**：11 类均有结果或明确的 `UNKNOWN`；命中证据可追溯；缺图、模型异常与无效输出不会默认产生 `NOT_HIT`，未校准分数不会伪装为概率。

### Phase 4：固定数据集扩充与 TMT 离线对照

**目标**：在前期样本基础上形成独立评估，验证整体效果与覆盖率，不改变线上链路。

工作项：

- 扩充正例、反例、边界与真实抽样样本，按素材及近重复组划分开发集、验证集和独立测试集。
- 完成人工标注，同批固定素材分别运行 JEV 流程与 TMT，记录输入差异和 Ground Truth 局限。
- 按标签计算 Accuracy、Precision、Recall、F1、False Negative Rate、UNKNOWN Rate 与 Coverage。
- 只有分数语义符合 7.5 的前提时，才验证 `>=0.85`、`<=0.30` 的原始分层假设，并在验证集上选择标签级阈值；否则先评估分类质量。
- 对不一致样本人工复核，分析是否需要调整标签定义、输入组织或可选增强，不用测试集反复调参。

**交付物**：固定数据集 V1、JEV/TMT 对照、分标签指标、误报/漏报案例、适用时的阈值建议。

**退出条件**：90% 指标的分母和未知样本口径明确，漏判与覆盖率单独评估，结论基于人工复核或明确说明真值局限。

### Phase 5：动态 ADM 专项验证

**目标**：逐步验证动态 HTML5、JS Loader 和 MRAID 等素材的可提取性。

工作项： - 选取代表性 JS Loader ADM（例如前述 Jampp
类型）作为专项样本。 - 先做静态资源分析。 -
在隔离渲染环境中尝试获取最终素材截图。 -
记录外部资源加载链路和失败原因。 - 评估 MRAID/SDK
依赖对素材提取的影响。 - 对无法完整渲染的样本输出 `UNKNOWN`
或不完整状态。 - 禁止真实点击、曝光、转化和计费链路触发。

**交付物**： - 动态 ADM 样本集 - 隔离渲染方案 - 动态素材提取覆盖率报告 -
资源安全与失败原因分析

**退出条件**： - 渲染环境通过安全评审。 - 动态素材提取结果可追溯。 -
失败样本不会被误判为合规。

### Phase 6：Shadow Mode 影子运行

**目标**：在不影响线上审核结果的前提下，验证真实流量上的表现。

工作项： - 对符合采样和安全要求的 Banner Response 并行运行 JEV。 -
线上现有审核仍以 TMT 为准。 - JEV
结果仅记录，不参与放行、拦截或竞价链路决策。 - 按标签、DSP、ADM
类型、解析状态分析表现。 - 抽取 JEV/TMT 不一致样本进行人工复核。 -
监控资源消耗、耗时、失败率和异常波动。

**交付物**： - Shadow Mode 运行报告 - 线上样本分布分析 - 与 TMT
的分标签差异报告 - 人工复核案例集 - 运行成本与稳定性报告

**退出条件**： - 影子运行结果稳定。 -
关键标签的误报、漏报和未知比例达到业务可接受范围。 -
安全、性能、成本和审计能力通过评审。

### Phase 7：有限场景试运行与替代评估

**目标**：在充分验证后，评估是否可对部分标签或流量范围进行有限试运行。

前置条件： - Phase 0--6 的退出条件全部满足。 -
业务审核负责人确认可接受的漏放风险。 -
有人工复核、回滚、审计和异常降级机制。 -
已明确模型不可用、素材解析失败、输入不完整时的处理策略。 - 已明确 TMT
保留策略和回退方式。

建议策略： - 不一次性替换全部 11 类。 -
优先选择数据充分、边界清晰、评估结果稳定的标签或样本范围。 -
其余标签继续使用 TMT。 - 初期保留人工复核和可回滚机制。 -
任何阈值变化都要经过离线回归测试。

**交付物**： - 有限试运行评审报告 - 上线/回滚方案 - 标签级路由策略 -
运行监控与审计看板

**退出条件**： - 业务、研发、审核、安全相关方共同批准。 -
回滚演练通过。 - 试运行期间关键指标无不可接受退化。

## 13. 测试用例规划

### 13.1 标签正反例

每个标签至少准备： - 明确正例。 - 语义相似但不违规的反例。 -
容易与其他标签混淆的边界样本。 - 多标签同时出现的组合样本。

### 13.2 ADM 解析用例

  用例             输入特征                预期
  ---------------- ----------------------- -----------------------------------
  静态图片         ADM 直接引用图片        提取图片并生成 hash
  简单 HTML        HTML 中含图片和文案     提取图片和文本
  多图片           一个 ADM 引用多张图片   每张图片独立标识
  JS Loader        脚本运行后加载素材      静态解析并记录动态依赖
  Iframe           ADM 内含 Iframe         记录 Iframe URL，不默认信任其内容
  资源 404         图片资源不可访问        标记提取失败，不判为合规
  超时资源         外部资源加载超时        记录超时和 UNKNOWN 原因
  MRAID 依赖       依赖广告 SDK 环境       标记环境依赖
  Tracking Pixel   仅有像素追踪            标记缺少可审核主体素材

### 13.3 Unsecured Request 用例

-   实际引用的图片 URL 为 `http://`：命中。
-   实际引用的图片 URL 为 `https://`：不命中。
-   ADM 注释中出现 `http://`，但没有实际资源引用：不应仅凭字符串命中。
-   URL 动态拼接且无法还原：标记未知或待检查。
-   `imp.secure` 缺失：不能单独命中。
-   `nurl` / `burl` 为
    HTTP：按最终确认的业务范围分别判断，不与创意资源规则混淆。

### 13.4 结果协议测试

-   11 类标签字段齐全。
-   每个 `HIT` 有证据。
-   `UNKNOWN` 有原因。
-   `NOT_HIT` 对应的检测输入完整度满足要求。
-   概率/分数范围合法，空值处理一致。
-   相同固定输入和版本的重复运行结果符合稳定性要求。
-   模型超时、接口异常、解析失败均有明确状态，不得静默转换成未命中。
-   Hub 只返回部分标签时，其余标签保持 `UNKNOWN`，不能按空值补成 `NOT_HIT`。
-   分数、概率与置信度不混用；缺失分数、解释或区域坐标时不补造。
-   输出中的来源 ID 必须属于本次实际送审素材，无法建立命中证据关联时进入复核。

### 13.5 Hub 与多模态接入用例

| 用例 | 验证点 |
| --- | --- |
| 接口路由 | 实际请求为 `POST /v1/responses`，无重复 `/v1`；模型字段为 `jev-1.14` |
| 鉴权与保密 | 正确鉴权可用；无效密钥有明确错误；前端、日志、错误消息和素材请求不泄露密钥 |
| 文本与单图 | 分别验证文字输入、真实图片输入，以及图文联合输入的协议和结果 |
| 图片替换/移除 | 相同指令下切换不同内容的图片、移除图片形成对照，核验视觉输入真实参与判断 |
| 多图与来源 | 结果可关联具体素材或整体截图，不把所有输入笼统当作某个命中标签的证据 |
| 坏图与限制 | 图片损坏、格式不支持、请求过大或多图超限时有明确失败状态 |
| 响应不完整 | Hub 接受请求但图片被忽略、标签缺项、格式无效时，不视作完整审核成功 |
| 超时与限流 | 明确错误、复核和重试预算，不无限重试或静默放行 |
| 注入文案 | 图片/ADM 中的指令性文字不能覆盖标签定义、输出约束或服务地址 |
| 可选 OCR | 不启用 OCR 仍可运行基础链路；是否启用由对照效果决定，不把 OCR 失败自动等同于全部标签未知 |
| 版本与回归 | Hub 模型映射变更可追踪，固定样本可重复执行并比较结果 |

## 14. 安全、隐私与运行风险

### 14.1 动态代码安全

ADM 中的第三方 JavaScript 不可信。必须： -
使用隔离容器或隔离浏览器环境。 - 限制网络出口和可访问域名。 -
禁止访问内网、云元数据地址和本机敏感服务。 -
限制执行时间、CPU、内存、页面大小、资源数量。 -
禁止真实点击、曝光、转化和计费事件。 - 不复用开发人员登录态、Cookie
或本机浏览器配置。 - 对下载资源进行类型校验和大小限制。 -
对异常样本进行隔离和审计。

### 14.2 结果风险

  风险                 影响                     建议措施
  -------------------- ------------------------ -----------------------------------
  ADM 解析不完整       漏掉实际创意素材         记录解析覆盖率，失败标记 UNKNOWN
  动态资源变化         同一 CRID 结果不一致     保存资源 hash 和采集时间
  模型误判             误拦或漏放               分标签评估，Shadow Mode，人工复核
  分数未校准           阈值不可靠               验证 score 语义，必要时做校准
  TMT 结果不等于真值   评估偏差                 建立人工复核 Ground Truth
  外部 JS 风险         触发恶意行为或真实计费   沙箱、网络隔离、禁用交互
  数据集偏差           离线指标虚高             真实流量抽样、独立测试集
  标签定义变化         历史结果不可比           标签版本化和回归测试

------------------------------------------------------------------------

### 14.3 Hub 调用与素材隐私

- 按 7.6.3 处理当前 HTTP 入口的明文传输风险；确认安全通道后再携带密钥和真实素材联调。
- Hub 密钥仅在后端使用，鉴权信息不进入素材快照、普通日志、版本记录或前端响应。
- 安全出口策略同样适用于静态图片下载，不只约束动态浏览器；下载时检查重定向和目标地址，避免访问内网、云元数据或本机敏感服务。
- 仅发送审核所需图文与字段，确认自有 Hub 是否继续转发上游、上下游留存策略和允许处理的数据范围，不因为入口自有就假设素材不离开内部系统。
- Hub 失败或图像未被透传时，相关模型标签进入 `UNKNOWN`/复核；不能因 HTTP 调用成功而判定审核成功。

## 15. 监控与运行指标

建议按模块建设监控：

### 15.1 解析与提取

-   Response 解析成功率。
-   ADM 类型分布。
-   ADM 解析成功率。
-   图片提取成功率。
-   动态渲染成功率。
-   外部资源加载失败率。
-   平均/分位处理耗时。

- 语义明确时的分标签 score/probability 分布，无可用分数时不生成该指标。
- 重复运行一致性与实际模型映射变化。
- 单条样本端到端耗时、Hub 调用耗时及成本；启用 OCR 后单独比较增量成本和质量收益。

### 15.3 质量评估

-   分标签 Precision、Recall、F1、Accuracy。
-   False Negative Rate。
-   与 TMT 不一致率。
-   人工复核推翻率。
-   高置信样本准确率。
-   UNKNOWN 原因分布。

## 19. 待确认事项

已确认自有 Hub 地址、Bearer 鉴权和 `jev-1.14` 模型标识，不再把“选择哪种接入方式”作为悬而未决事项；以下按对应阶段推进确认，不要求一次性完成全部后续治理：

1. **Phase 0**：Hub `/v1/responses` 的完整请求/返回样例是什么？文本、单图、多图、非流式输出、字段限制与错误码如何定义？
2. **Phase 0**：Hub 是否实际透传图片？上游图像选项由 Hub 内部启用还是项目传入？`jev-1.14` 对应哪个实际上游版本，映射变更如何通知？
3. **Phase 0**：标签、分数、解释和素材来源能否返回？原生 `noul`、`choice`、`score`、`box` 是否有映射，哪些能力在本项目无需使用？
4. **联调前**：当前 HTTP 入口通过什么加密通道访问，或是否提供 HTTPS？密钥如何注入、素材是否转发上游、数据留存和脱敏策略如何约束？
5. **Phase 0–2**：`Unsecured Request` 是否包含 `nurl`、`burl` 或点击地址？最小样本与后续各标签正负样本的数量、人工标注资源如何安排？
6. **Phase 3–4**：哪些标签确有必要增加 OCR 或独立视觉增强？没有有效分数时采用什么分类质量门槛，有分数时如何验证其语义与校准？
7. **Phase 4**：TMT 11 类结果能否批量获取？90% 指标的统计范围、未知样本分母、分标签漏判门槛和覆盖率要求是什么？
8. **Phase 5–6**：动态素材允许的外网访问范围、资源限制、采样比例、数据保留周期和预算是多少？
9. **Phase 7**：哪些标签/流量允许有限试运行，哪些必须保留 TMT 或人工复核？

## 20. 最终建设路径总结

``` text
确认 Hub 传输安全与接入协议 + 标签规范 + 最小开发样本
    ↓
POST /v1/responses，model = jev-1.14
验证真实图片输入、文本输入与可用输出
    ↓
Bid Response / ADM 解析
    ↓
安全获取真实素材 + 多模态输入组装
    ↓
JEV 直接图文判断（10 类）+ URL 规则（1 类）
    ↓
统一 11 类结果、证据与 UNKNOWN
按效果决定是否增加 OCR / 外部视觉增强
    ↓
扩充固定数据集 + 人工标注 + 独立测试集
    ↓
TMT 离线对照与分标签评估
    ↓
动态 ADM 隔离渲染专项验证
    ↓
Shadow Mode 真实流量验证
    ↓
有限场景试运行评审
    ↓
再决定是否逐步替代部分 TMT 能力
```

**核心结论**：采用自有 Hub 接入 `jev-1.14`，优先验证 JEV 直接理解图片与文案，不预先建设强制性的“外部视觉特征提取 → JEV 决策”链路；安全素材获取、URL 规则、证据关联和未知状态治理仍由项目侧负责。先验证图文通路与最小样本，再扩展工程和质量评估，只有覆盖率、分标签效果、安全性与成本通过验证后才评估有限替代 TMT。
